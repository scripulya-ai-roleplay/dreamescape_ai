# Ферма STM32MP1/MP2: план разработки и инфраструктуры

Сервис на Go раскатывает приложения на разных стеках на ферму плат STM32MP1/MP2. Управление идёт через SPA-панель, и в ней не нужно думать о том, что внизу STM32.

Проект домашний и для резюме, поэтому продакшен-оптимизации сознательно не нужны. Где можно упростить, план упрощает (см. [раздел 9](#9-что-сознательно-упрощаем)).

**Принятые решения:**
- железо — STM32MP1/MP2, приложения запускаются в Docker под Linux;
- прошивки для Cortex-M-ядра пишутся на Zephyr;
- панель управления — SPA на React и TypeScript;
- сервис состоит из трёх частей: оркестратор с инвентаризацией, отдельный builder образов и агент на каждой плате.

## 0. Ключевые решения и важные уточнения

- **Железо — STM32MP1/MP2.** Приложения работают в Docker под Linux на ядрах Cortex-A. Поэтому исходная цель — раскатывать приложения на любых стеках и не думать, что внизу STM32, — достижима почти полностью.
- **Zephyr работает на втором ядре того же чипа.** Это Cortex-M-сопроцессор: M4 у MP15, M33 у MP2. Прошивку на него загружает Linux через remoteproc — как обычный файл, без программатора и SWD. Контейнеры общаются с прошивкой через RPMsg.
- **Агент работает по модели желаемого состояния (target state)**, как kubelet в Kubernetes. Оркестратор описывает, каким должно быть состояние платы, а агент сам приводит к нему контейнеры и прошивку. Команды вида «прошей плату X» не нужны.
- **Builder** собирает через BuildKit образы сразу под две архитектуры (arm/v7 для MP1, arm64 для MP2) и Zephyr-прошивки.
- **Фронтенд** — SPA на React и TypeScript.
- **По сравнению с первой версией плана** (под Cortex-M без Linux) ушли probe-rs/SWD, USB-хабы, Renode, MicroPython и WASM-рантаймы. Платы Nucleo с прошивкой по SWD остались в [идеях на потом](#идеи-на-потом).

> **Важно про Zephyr.** Docker и Zephyr на этих чипах не конкурируют, а работают рядом. Docker запускается только под Linux на Cortex-A, а Zephyr — это RTOS для Cortex-M. Теоретически Zephyr умеет работать и на некоторых Cortex-A, но тогда на них не будет Linux, а значит, и Docker.
>
> Про «широкую поддержку»: для M-ядер MP1/MP2 в Zephyr всего несколько плат. Выбор всё равно удачный. Связь с Linux (OpenAMP/RPMsg) и загрузка через remoteproc есть из коробки. А тот же код потом соберётся под обычные STM32-микроконтроллеры, если расширишь ферму.

## 1. Железо: что важно знать про STM32MP1/MP2

| Линейка | Ядра для Linux и Docker | Платформа образов | M-ядро для Zephyr | Пример платы |
|---|---|---|---|---|
| STM32MP13 | 1× Cortex-A7 | linux/arm/v7 | нет | STM32MP135F-DK |
| STM32MP15 | 1–2× Cortex-A7 | linux/arm/v7 | Cortex-M4 | STM32MP157F-DK2, STM32MP157D-DK1 (512 МБ RAM) |
| STM32MP2 (MP25) | 1–2× Cortex-A35 | linux/arm64 | Cortex-M33 | STM32MP257F-DK (4 ГБ RAM), STM32MP257F-EV1 |

Что из этого следует:
- **Одна плата — один узел (нода) кластера.** Ферма превращается в маленький ARM-кластер, и ты фактически пишешь мини-balena или мини-Kubernetes.
  - Ближайший аналог — balenaCloud/openBalena. Там агент на устройстве сам забирает желаемое состояние, отдельный builder собирает ARM-образы, а дашборд управляет всем парком устройств.
  - Полезно также посмотреть модели Kubernetes (kubelet, Deployment, DaemonSet) и Nomad (job, allocation).
- **Две архитектуры процессоров.** Образы нужно собирать под обе, а планировщик должен учитывать платформу.
- **M-ядро занимает одно приложение:** на плате одновременно может работать только одна прошивка.
- **Ресурсов мало** (512 МБ на MP15 DK). Поэтому лимиты памяти и учёт ресурсов в планировщике — настоящая задача, а не формальность.

## 2. Архитектура

```text
        SPA (React)                 farmctl (CLI)
             |                            |
             | HTTP/JSON + стримы         | gRPC
             v                            v
 +----------------------------------------------+  задания на сборку  +--------------------+
 |                 orchestrator                 | ------------------> |      builder       |
 |  API, инвентарь, планировщик, reconcilers,   | <------------------ |  BuildKit: образы  |
 |  target state нод, события, раздача SPA      |    статусы, логи    |  и Zephyr-прошивки |
 +-----+-------------------------^--------------+                     +---------+----------+
       |                         |                                              |
       v                         |                                              | push
  PostgreSQL                     | gRPC-стрим                                   v
                                 | (агент подключается сам)           +--------------------+
                                 |                                    | OCI registry (zot) |
                                 |                                    | образы arm/v7 и    |
                                 |                                    | arm64, прошивки    |
 +-------------------------------+----------------------------+       +---------+----------+
 |  Плата STM32MP1 / MP2                                      |                 |
 |                                                            | <--- pull ------+
 |  Cortex-A (Linux):   agent ---Docker API---> контейнеры    |      по digest
 |                        |                        |          |
 |                        | remoteproc             | RPMsg    |
 |                        v                        |          |
 |  Cortex-M (Zephyr):  прошивка <-----------------+          |
 +------------------------------------------------------------+
```

- **orchestrator** — управляющий сервис:
  - API для SPA и CLI, учёт плат;
  - приложения, сборки, релизы, деплойменты;
  - планировщик и циклы согласования (reconcilers), расчёт желаемого состояния для каждой платы;
  - лента событий, проксирование логов и терминала;
  - раздаёт встроенную SPA, бинарники агента и скрипт установки.
- **builder** — исполнитель сборок:
  - клонирует репозиторий и читает манифест приложения;
  - через BuildKit собирает образы под нужные платформы и Zephyr-прошивки под нужные платы;
  - считает размеры, загружает результат в registry, транслирует логи в реальном времени.
- **agent** — по одному на плату, работает под Linux как systemd-сервис:
  - сам подключается к оркестратору, поэтому работает за NAT и не открывает входящих портов;
  - сообщает параметры платы и приводит Docker и M-ядро к желаемому состоянию;
  - отправляет статусы, логи и метрики, выполняет команды внутри контейнеров (exec).
- **zot** — registry: хранит образы под обе архитектуры и прошивки в формате OCI.
- **SPA и farmctl** — клиенты API.

### Почему желаемое состояние, а не команды

При каждом подключении агент получает полное описание того, что должно работать на плате. Агент сравнивает его с фактическим: свои контейнеры он узнаёт по меткам, плюс проверяет текущую прошивку. Затем устраняет разницу.

Поэтому обрывы связи, повторная доставка и перезапуск агента ничего не ломают. Идентификаторы операций и подтверждения отдельных команд не нужны. Командами остаются только разовые действия: перезагрузка, рестарт, exec, просмотр логов.

## 3. Доменная модель

- **Node** — плата с агентом:
  - ID (генерирует агент при первом запуске), hostname, IP;
  - модель (определяется по полю compatible в device tree), платформа, CPU/RAM/диск, версии ОС, ядра, Docker и агента;
  - M-ядро: есть ли оно, его состояние и текущая прошивка;
  - метки и память, доступная приложениям;
  - статус: Pending (ждёт подтверждения) → Ready / NotReady; отдельно Cordoned (выведена из планирования) и Draining (освобождается).
- **Каталог плат** — YAML-файл в репозитории.
  - Ключ — compatible из device tree.
  - Значение — модель, платформа, тип M-ядра, имя платы в Zephyr, особенности (GPU, NPU у MP257 и т.п.).
  - На каталоге держится независимость от железа: пользователь пишет «прошивка для M-ядра», а builder сам знает, под какие платы её собрать.
- **App** и манифест в репозитории приложения (например, `farm.yaml`):
  - контейнеры: Dockerfile или шаблон стека (Go/Python/Node/статика), порты, env, тома, лимиты, проверка здоровья (HTTP/TCP/команда), политика перезапуска;
  - необязательная прошивка: путь к Zephyr-приложению, строка-маркер готовности в логе, каналы RPMsg для проброса в контейнеры.
- **Build** — сборка одного коммита. Состоит из задач «компонент × платформа или плата». Хранит статус, логи, digest-и, размеры образов и заполнение flash/RAM прошивкой.
- **Release** — неизменяемый набор: образы и прошивки по платам (всё по digest) плюс конфиг. Выкатывают и откатывают именно релизы.
- **Deployment** — желаемое состояние:
  - релиз и правило выбора плат;
  - режим: N копий или «на каждую подходящую плату» (как DaemonSet);
  - стратегия: Recreate, Rolling с ограничением maxUnavailable или Canary;
  - политика отката.
- **Instance** — экземпляр деплоймента на конкретной плате (аналог Pod или Allocation).
  - Фазы: Pending → Pulling → LoadingFirmware → Starting → Running, либо Unhealthy, Failed, Lost.
  - Хранит число рестартов и последнюю ошибку.
- **NodeTargetState** — вычисляемое: все Instance платы и номер версии (generation). Агент отвечает номером, который уже применил (observedGeneration). Так видно, догнала ли плата изменения.
- **Event** — лента событий и аудит.

## 4. Сквозной сценарий

1. Создаёшь App в SPA или командой `farmctl apply`.
2. Нажимаешь «Build». Builder собирает:
   - образы под платформы, которые есть в ферме (или указаны в манифесте), и публикует их под общим multi-arch тегом;
   - прошивку под Zephyr-платы всех моделей с подходящим M-ядром.

   Логи сборки идут в SPA в реальном времени.
3. Из успешной сборки получается релиз.
4. Создаёшь Deployment формой или в YAML-редакторе. Планировщик оставляет только платы, которые:
   - в статусе Ready и не выведены из планирования;
   - имеют платформу, под которую есть образ;
   - имеют свободное M-ядро нужной модели (если в релизе есть прошивка);
   - имеют достаточно памяти, не конфликтуют по портам и подходят по меткам.

   Из подходящих он выбирает наименее загруженные и старается разнести копии по разным платам. Затем создаёт Instance и обновляет желаемое состояние плат.
5. Агент получает новое желаемое состояние и по порядку:
   - скачивает образы по digest (Docker сам выбирает нужную архитектуру);
   - если есть прошивка: скачивает её и проверяет digest, останавливает M-ядро, загружает новую прошивку, запускает ядро и ждёт маркер готовности;
   - запускает контейнеры с метками, лимитами и пробросом устройств RPMsg;
   - проверяет здоровье и отправляет статусы.
6. При стратегии Rolling следующая партия плат обновляется, только когда предыдущая здорова. Если проверка провалилась, система откатывается на прошлый релиз. Его образы и прошивку агент держит в кэше.
7. Если плата пропала, она становится NotReady. После паузы её копии переезжают на другие подходящие платы.
8. В SPA видны логи контейнеров и M-ядра, метрики, терминал в контейнер, история событий.

## 5. Технологии: бэкенд, builder, агент

Вниз — желаемое состояние и разовые команды | Агент опрашивает желаемое состояние по HTTP (long-poll) и отправляет статусы POST-запросами. Так устроен агент у balena |
| База данных | PostgreSQL, pgx + sqlc, миграции через goose | — |
| Задания на сборку | NATS JetStream | без брокера: очередь заданий в Postgres (например, River) |
| Registry | zot: образы и артефакты OCI, лёгкий, есть веб-интерфейс | CNCF Distribution |
| Прошивки как OCI-артефакты | oras-go | — |
| Сборка образов | buildkitd в контейнере + Go-клиент BuildKit. QEMU binfmt для ARM, кэш слоёв в registry | на старте — docker buildx через os/exec |
| Сборка Zephyr | Тот же BuildKit: Dockerfile на базе официального образа Zephyr с SDK, west, кэш модулей и ccache. Результат выгружается файлами и загружается в registry как OCI-артефакт. Builder-у не нужен доступ к Docker-сокету | запуск контейнера Zephyr через Docker SDK |
| Агент: контейнеры | официальный Go SDK Docker Engine через локальный сокет | Go-клиент containerd |
| Агент: M-ядро | интерфейс remoteproc в sysfs. Логи — через trace-буфер remoteproc и RPMsg-tty | — |
| Агент: метрики | gopsutil + Docker stats API | node_exporter на плате |
| Агент: сборка и установка | Go без cgo, кросс-компиляция под linux/arm (GOARM=7) и linux/arm64. systemd-юнит, скрипт установки с токеном | — |
| Наблюдаемость | slog, Prometheus, Grafana, OpenTelemetry | только slog и /metrics |
| CLI | cobra | — |

## 6. Фронтенд (SPA)

### Стек

- React + TypeScript + Vite.
- Библиотека компонентов — одна из двух:
  - **Mantine** — проще всего получить красивый дашборд без дизайнера: таблицы, формы, уведомления, графики и тёмная тема есть из коробки;
  - **shadcn/ui + Tailwind** — модно и гибко, но больше ручной сборки.
- Данные и роутинг: TanStack Query (кэш серверных данных, обновление по событиям), TanStack Router или React Router.
- Компоненты:
  - таблицы — TanStack Table или mantine-react-table поверх неё;
  - графики — Recharts (на нём построены Mantine Charts) или ECharts;
  - логи и терминал — xterm.js;
  - YAML-редактор — Monaco;
  - схема фермы — React Flow;
  - формы — react-hook-form + zod.
- API-клиент только сгенерированный, типы руками не пишутся.
- Живые данные:
  - статусы, прогресс и логи — через серверные стримы Connect или SSE;
  - WebSocket — только для интерактивного терминала, потому что Connect в браузере не поддерживает двусторонние стримы.

### Сборка и авторизация

- При разработке — dev-сервер Vite с прокси на API.
- В сборке статика встраивается в бинарник оркестратора (пакет embed). Один бинарник отдаёт и API, и SPA, поэтому не нужны ни CORS, ни отдельный nginx.
- Один администратор, страница входа, сессия в cookie с флагами HttpOnly и SameSite.

### Экраны

1. Dashboard: платы по статусам, суммарные ресурсы, активные выкатки, последние события.
2. Платы: таблица со статусом, платформой, моделью, CPU/RAM и M-ядром.
   - В карточке платы: параметры, графики, контейнеры, состояние и консоль M-ядра.
   - Действия: подтвердить, вывести из планирования, освободить, перезагрузить.
3. Схема фермы: платы, их M-ядра и что где запущено.
4. Приложения и сборки: живые логи, размеры образов по платформам, заполнение flash/RAM прошивкой.
5. Релизы: состав, платформы, платы.
6. Деплойменты:
   - создание формой или в YAML;
   - прогресс выкатки по платам и статусы Instance;
   - кнопка отката и история версий.
7. Логи с фильтром и автопрокруткой; веб-терминал в контейнер.
8. Лента событий.
9. «Добавить плату»: команда установки агента с токеном в одну строку.

### Чтобы выглядело хорошо без дизайнера

- Возьми готовый шаблон админки под выбранную библиотеку и не изобретай раскладку.
- Сделай единую палитру статусов (Running — зелёный, Deploying — синий, Pending — жёлтый, Failed — красный) и цветные метки.
- Тёмная тема по умолчанию, заглушки (skeleton) при загрузке, всплывающие уведомления, анимированный прогресс выкатки.
- Как можно больше живых данных — на демо это производит главное впечатление.

### Тесты фронтенда

Проверка типов, ESLint, Vitest для логики и один Playwright-тест основного сценария.

## 7. Инфраструктура для разработки

### 7.1. Железо

- **Минимальный набор:**
  - 1× STM32MP257F-DK — основная рабочая плата: arm64, 4 ГБ, M33, NPU;
  - 1–2× STM32MP157F-DK2 или более дешёвая DK1 без дисплея и Wi-Fi: arm/v7, 512 МБ, M4.

  Так сборка под две архитектуры и планировщик имеют смысл. Можно добавить STM32MP135F-DK — плату без M-ядра. На ней видно, что планировщик не отправляет туда прошивки.
- **До покупки** проверь в документации Zephyr, поддерживается ли M-ядро твоей платы. Например, есть платы `stm32mp157c_dk2` (M4) и `stm32mp257f_ev1` (M33). Если твоей нет, придётся сделать своё описание платы на основе существующего. Это хороший опыт, но лишняя работа.
- **Питание:** качественные блоки USB-C нужной мощности. От недостатка питания под нагрузкой бывают случайные перезагрузки. По желанию — умные розетки с локальным API (Shelly, Tasmota), чтобы оркестратор мог принудительно перезагрузить зависшую плату.
- **Сеть:** проводной Ethernet через коммутатор и закреплённые адреса в DHCP.
- **Хранилище:** microSD класса A1/A2 от 32 ГБ, лучше повышенной износостойкости (high endurance). Docker много пишет на диск.
- **Консоль:** встроенный ST-LINK на DK-платах даёт serial-консоль Linux по USB. Пока поднимаешь плату, держи её подключённой к ПК.
- **Рабочий ПК** — на нём работают оркестратор, builder и registry. По желанию — отдельный arm64-компьютер (например, Raspberry Pi 5) как дополнительный исполнитель BuildKit. Он собирает arm64 и arm/v7 без медленной эмуляции QEMU.

### 7.2. ОС на платах (выбрать в фазе 0)

1. **Готовый образ Debian/Ubuntu для твоей платы** от производителя или сообщества, если найдётся. Это самый быстрый путь: Docker ставится пакетом.
2. **OpenSTLinux (дистрибутив ST на Yocto) со слоем meta-virtualization.** Официальный путь: свой образ с Docker, нужными опциями ядра и агентом. Настраивать дольше, зато из этого потом вырастет «золотой образ» фермы. И это плюс для резюме: Yocto ценится в embedded.
3. **Buildroot с пакетом Docker.** Проще Yocto, но готового от ST меньше. Проверь, есть ли конфигурация под твою плату — в самом Buildroot или во внешнем дереве от ST.

Готовый Starter Package от ST, скорее всего, идёт без Docker — это тоже проверить в фазе 0. Он удобен для первого знакомства с платой и сэмплами M-ядра, но для фермы понадобится один из вариантов выше.

### 7.3. Подготовка платы: обязательный минимум

- **Ядро:** проверь его скриптом `check-config.sh` из репозитория moby (cgroups, namespaces, overlayfs, netfilter, bridge, veth). Недостающие опции включи в конфигурации ядра.
- **Время:** NTP (systemd-timesyncd или chrony) должен синхронизироваться до старта агента. На DK-платах, как правило, нет батарейки для RTC: после перезагрузки часы сбиваются, а с ними ломается TLS.
- **Docker** (файл daemon.json):
  - доверие к registry: свой CA (лучше) или insecure-registries для домашнего zot;
  - ротация логов контейнеров;
  - live-restore, чтобы контейнеры переживали перезапуск dockerd.
- **SSH** — только по ключам.
- **M-ядро:** есть /sys/class/remoteproc, драйвер RPMsg-tty доступен, сэмпл Zephyr загружается и отвечает.
- **Имя и адрес:** hostname по шаблону (например, mp1-01, mp2-01) и закреплённый IP.

### 7.4. Подключение новых плат

1. **На старте — вручную:** скопировать на плату бинарник агента, конфиг (адрес оркестратора и токен) и systemd-юнит.
2. **Потом — мастер «Добавить плату» в SPA:**
   - оркестратор выдаёт одноразовый токен и команду установки в одну строку;
   - скрипт определяет архитектуру, скачивает с оркестратора агент нужной сборки, ставит юнит и запускает его;
   - плата появляется в панели со статусом Pending, ты её подтверждаешь;
   - после подтверждения агент получает постоянные учётные данные платы.
3. **Ещё позже — «золотой образ» на Yocto** с предустановленным агентом: записал SD-карту, включил плату, подтвердил в панели.

### 7.5. Виртуальная ферма: разработка без железа

- **Виртуальная плата** — контейнер с агентом и Docker-in-Docker. В Compose их можно размножить до нужного числа.
- **Платформа:** виртуальные платы могут честно быть amd64 (быстро) или притворяться arm/v7 и arm64 через QEMU binfmt (медленно, зато проверяет мультиархитектурность).
- **Модель платы** в режиме симуляции задаётся в конфиге агента вместо чтения device tree.
- **Фейковый remoteproc:** дерево каталогов, повторяющее sysfs (firmware, state, trace), и небольшой симулятор. Он «запускает» прошивку, пишет лог с маркером готовности, по команде «падает» в состояние crashed и поднимает фейковый RPMsg-канал (pty).
- Агент работает с M-ядром через интерфейс с двумя реализациями — настоящей и фейковой. Это же упрощает unit-тесты.
- CI гоняет e2e-тесты на виртуальной ферме.

### 7.6. Docker Compose для разработки

Профили:
- **core** — PostgreSQL, NATS, zot, buildkitd (с установкой QEMU binfmt), orchestrator, builder;
- **virtual-farm** — несколько виртуальных плат с фейковым remoteproc;
- **observability** — Prometheus, Grafana, Jaeger или Tempo с OTel Collector.

Плюс:
- SPA при разработке запускается dev-сервером Vite на хосте и проксирует API на оркестратор.
- Taskfile (или Makefile) с задачами: поднять окружение, сгенерировать код (buf, sqlc), применить миграции, прогнать тесты, собрать агент под ARM и выложить его на плату по SSH.

### 7.8. CI/CD (GitHub Actions)

- **Go:** golangci-lint, unit-тесты, интеграционные тесты на testcontainers-go.
- **Агент:** бинарники под linux/arm (v7) и linux/arm64 через goreleaser, публикация в релизы.
- **Образы сервисов** (orchestrator, builder): сборка и публикация в registry.
- **Фронтенд:** проверка типов, ESLint, Vitest, сборка.
- **Актуальность сгенерированного кода:** CI заново генерирует код из proto и SQL (buf, sqlc) и падает, если в git появились изменения.
- **Zephyr:** сборка примеров прошивок в официальном образе Zephyr.
- **e2e на виртуальной ферме:** apply → Running → HTTP-проверка → выкатка новой версии → релиз со сломанной проверкой здоровья → автоматический откат.
- **Тесты на реальном железе (hardware-in-the-loop):** self-hosted runner дома гоняет smoke-тест на настоящих платах. Только в приватном репозитории: в публичном чужой PR может запустить свой код на твоём runner-е внутри домашней сети. Если основной репозиторий публичный (для резюме), держи HIL-тесты в отдельном приватном репозитории или запускай smoke-тест вручную через farmctl.

### 7.9. Доступ и безопасность

- Панель и API доступны только из домашней сети или через Tailscale/WireGuard. Наружу не выставлять.
- Доступ к Docker-сокету на плате равен root. Для домашнего проекта это приемлемо, но держи в голове.
- Секреты (токены, пароль администратора) — в `.env`, который не коммитится.

## 8. Этапы разработки

### Фаза 0. Bring-up плат, без Go

- Поставить ОС на каждую плату, включить Docker, проверить ядро скриптом `check-config.sh`.
- Поднять zot на ПК. Собрать через buildx простой multi-arch образ (arm/v7 + arm64), загрузить в zot и запустить на MP1 и MP2.
- Собрать сэмпл Zephyr с OpenAMP (например, `openamp_rsc_table`) под M-ядро. Загрузить его через remoteproc, увидеть логи и обменяться сообщениями через `/dev/ttyRPMSG*` из контейнера (с пробросом устройства).
- Для MP2: выяснить, нужна ли подпись прошивки M33 и загрузка через OP-TEE.
- Набросать каталог плат: compatible → модель, платформа, M-ядро, имя платы в Zephyr.
- Записывать все команды в `docs/bring-up.md`. Это готовый материал для README и основа для автоматизации.

**Готово, когда:** на каждой плате руками запускается контейнер из своего registry. На платах с M-ядром ещё и прошивка, а контейнер обменивается с ней данными через RPMsg.

### Фаза 1. Каркас

- Монорепозиторий, Taskfile, golangci-lint, CI с линтерами и тестами.
- Compose-профиль core.
- proto v1 (сущности и сервисы), генерация Go и TS через buf.
- Загрузчик каталога плат с валидацией.
- Скелет SPA (раскладка, роутинг, тема, страница входа), встроенный в бинарник оркестратора.

**Готово, когда:** одна команда поднимает окружение, оркестратор отдаёт SPA и отвечает на запрос версии через сгенерированный клиент, CI зелёный.

### Фаза 2. Агент сам по себе

- Адаптер Docker:
  - создание, запуск, остановка и удаление контейнеров с метками владения;
  - подписка на события Docker;
  - сборка мусора образов с сохранением образов предыдущего релиза для отката.
- Локальный reconciler: желаемое состояние из YAML-файла превращается в контейнеры на плате. Идемпотентность, повторы с backoff.
- Адаптер remoteproc и его фейковая реализация:
  - остановка ядра, смена прошивки, запуск;
  - обработка состояний crashed и attached;
  - ожидание маркера готовности;
  - кэш прошивок и откат на предыдущую.
- Сбор параметров платы (модель по compatible, платформа, ресурсы, M-ядро) и метрик.

**Готово, когда:** агент на реальной плате по YAML-файлу поднимает контейнер и прошивку и сам восстанавливает их после ручного вмешательства (удалил контейнер — он вернулся). Unit-тесты проходят на фейках.

### Фаза 3. Оркестратор: инвентарь и связь с агентами

- Схема БД и миграции.
- Регистрация плат по токену и подтверждение в панели.
- Двусторонний стрим, heartbeat, перевод в NotReady по таймауту, переподключение агента.
- Желаемое состояние плат с generation и observedGeneration.
- Ручное действие «запустить образ на плате» без планировщика — для проверки всей цепочки.
- SPA: список плат, карточка платы, живые статусы, логи контейнера по запросу.

**Готово, когда:** в панели видны все платы (реальные и виртуальные) с живыми метриками, отключённая от сети плата становится NotReady, а вручную назначенный контейнер запускается на выбранной плате.

### Фаза 4. Builder (MVP)

- Очередь заданий, клонирование репозитория, разбор манифеста.
- Сборка multi-platform образов через BuildKit, шаблоны стеков для приложений без Dockerfile.
- Сборка Zephyr-прошивки под каждую подходящую модель платы из каталога, отчёт о занятой flash/RAM.
- Загрузка образов и прошивок в zot, создание релиза.
- Живые логи сборки в SPA; страницы приложений, сборок и релизов.

**Готово, когда:** по кнопке в SPA репозиторий с Dockerfile и Zephyr-приложением превращается в релиз с образами под arm/v7 и arm64 и прошивками под каждую модель платы.

### Фаза 5. Декларативные деплойменты и планировщик

- Deployment как желаемое состояние и reconciler в оркестраторе.
- Планировщик: фильтры (платформа, M-ядро, память, порты, метки, cordon) и скоринг (разнос по платам, наименьшая загрузка).
- Стратегии Recreate, Rolling (maxUnavailable) и Canary. Следующая партия выкатывается, только если предыдущая здорова; при провале — автоматический откат.
- Перенос копий с пропавших плат, cordon и drain.
- SPA: создание деплоймента (форма и YAML в Monaco), прогресс выкатки по платам, история и откат.

**Готово, когда:** новая версия выкатывается партиями, сломанный релиз сам откатывается, а при выключении платы её копии переезжают на другие.

### Фаза 6. Связка «контейнер + прошивка» — главная фишка STM32

- Проброс устройств RPMsg в контейнеры: агент находит нужное устройство по имени канала, а не по номеру.
- Порядок запуска: сначала прошивка и маркер готовности, потом контейнеры.
- Атомарное обновление и откат всего набора: образы и прошивка вместе.
- Перезапуск зависимых контейнеров при перезапуске прошивки.
- Здоровье прошивки: состояние remoteproc плюс heartbeat через RPMsg.
- Каждая плата получает в желаемом состоянии прошивку, собранную именно под её модель.
- Демо: Zephyr мигает светодиодами, управляет PWM или читает датчик. Go-контейнер получает данные через RPMsg и отдаёт их по API, а SPA рисует живой график.

**Готово, когда:** приложение из контейнера и прошивки выкатывается одной кнопкой на MP1 и MP2 и целиком откатывается.

### Фаза 7. Полировка SPA и эксплуатация

- Dashboard и схема фермы на React Flow.
- Логи с фильтрами, веб-терминал (WebSocket → оркестратор → агент → docker exec), консоль M-ядра.
- Авторизация, аудит в ленте событий.
- farmctl умеет всё, что умеет панель.

**Готово, когда:** повседневную работу удобно делать из панели, а демо-сценарий прилично смотрится на видео.

### Фаза 8. Наблюдаемость и упаковка для резюме

- Метрики Prometheus (оркестратор, builder, агенты), дашборды Grafana, трейсинг OpenTelemetry по цепочке SPA → оркестратор → агент.
- README со схемой, GIF или видео демо, ADR по ключевым решениям (target state вместо команд, Connect, BuildKit, remoteproc).
- Описание проекта для резюме: какие задачи решены (согласование распределённого состояния, планировщик, стриминг, мультиархитектурная сборка, работа с железом).

**Готово, когда:** по README понятно, что это и как устроено, а демо-видео показывает путь от коммита до приложения, работающего на плате.

### Идеи на потом

- Слой Yocto с агентом и A/B-обновления ОС (RAUC или SWUpdate).
- Ноды на обычных STM32-микроконтроллерах (Nucleo) с прошивкой через probe-rs — на том же Zephyr-коде.
- NPU на MP257 (X-LINUX-AI): ML-модели как отдельный тип компонента.
- Встроенный reverse proxy и mDNS-имена для приложений.
- mTLS между агентом и оркестратором, управление секретами.
- Самообновление агента.

## 9. Что сознательно упрощаем

- Один экземпляр оркестратора, без отказоустойчивости и выбора лидера.
- PostgreSQL — единственный источник правды; события внутри оркестратора идут через pub/sub в памяти.
- Агенты аутентифицируются токенами, без mTLS.
- Без overlay-сети: контейнеры публикуют порты на хост, конфликты портов отсекает планировщик.
- Планирование только по памяти, CPU не учитывается.
- Одна прошивка на M-ядро; ядро эксклюзивно принадлежит одному Instance.
- Один администратор, без ролей и мультиарендности.
- Сборки запускаются кнопкой или из CLI, без вебхуков от Git-хостинга.
- Сами сервисы фермы запускаются в Docker Compose, без Kubernetes.

## 10. Подводные камни

- **MP1 — 32-битная платформа (arm/v7).** Готовых образов меньше, сборка через QEMU медленная. Go и Rust в Dockerfile лучше кросс-компилировать на платформе сборки, а не эмулировать компилятор.
- **512 МБ RAM на MP15 DK.** Лимиты памяти обязательны, тяжёлые рантаймы вроде JVM не подойдут, и на плате никогда ничего не собирать.
- **microSD изнашивается и работает медленно.** Маленькие образы, ротация логов, сборка мусора образов; журнал journald лучше держать в памяти.
- **Нет батарейки RTC:** после перезагрузки время неверное, отсюда ошибки TLS и «протухшие» токены. Таймауты heartbeat считать по часам оркестратора, а не платы.
- **Опции ядра для Docker** в готовых образах могут быть выключены (overlayfs, cgroups, netfilter).
- **Сеть Docker:** на минимальных образах бывают проблемы с iptables/nftables, из-за которых Docker не может настроить сеть контейнеров.
- **Периферия и память делятся между Linux и M-ядром в device tree:** какие таймеры, UART и пины отданы Cortex-M, где зарезервирована память под прошивку и буферы RPMsg. Начни со стандартных настроек ST и сэмплов Zephyr и меняй осторожно.
- **M33 на MP2** может требовать подписанную прошивку и загрузку через OP-TEE — проверить в фазе 0.
- **Состояния remoteproc:** attached означает, что ядро запустил загрузчик (сначала его надо остановить); crashed — что прошивка упала (агент должен уметь восстановить её).
- **Устройства RPMsg** появляются только после старта прошивки, а их номера могут меняться между запусками. Искать устройство по имени канала и запускать контейнеры только после его появления.
- **Мультиархитектурные образы:** если образ собран только под одну платформу, на плате другой архитектуры он не запустится. Планировщик должен смотреть на список платформ в индексе образа, а не на тег.
- **Docker-сокет = root.** Агент с доступом к сокету фактически root на плате.
